# 0014. Credit ledger and Fapshi mobile money checkout

**Date**: 2026-11-14
**Status**: In Progress

## Summary

Students buy prepaid credit packages in XAF with MTN MoMo and Orange Money through Fapshi direct collect prompts on their phones. A verified webhook allocates credits exactly once into the existing ledger, and failed AI runs refund automatically. You get a thin end to end thread first (packages plus checkout plus webhook plus balance), then status polling, history, and admin package controls.

## Requirements

**User stories**:
* As a student, I want to buy a credit package with my MoMo number so that I can spend credits on AI features.
* As a student, I want to see my balance and a low balance warning so that I never start work I cannot finish.
* As a student, I want a failed payment to show a clear retry path so that I am never stuck.
* As an administrator, I want to manage packages and reconcile payments against ledger entries so that support questions have answers.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
* **AC-1**: Student sees three active packages (Starter 1000 XAF for 50 credits, Standard 2500 XAF for 150 credits marked popular, Pro 5000 XAF for 350 credits) from the `CreditPackage` table, and picking one starts a checkout.
* **AC-2**: Student enters a Cameroonian phone in 9 digit local or 237 prefixed form, the server normalizes it to 237XXXXXXXXX, calls Fapshi direct collect for MTN MoMo or Orange Money, and the page polls payment status while the student approves the prompt on the phone.
* **AC-3**: Fapshi webhook with a valid HMAC signature moves the payment from PENDING to SUCCESSFUL and allocates package credits into the wallet exactly once; retried or replayed webhooks never credit twice.
* **AC-4**: An unpaid payment expires to EXPIRED after 30 minutes through a scheduled job, and expiry never allocates credits.
* **AC-5**: A FAILED or EXPIRED payment shows its reason with a retry action that creates a new payment row; the old row is never reused or mutated back to PENDING.
* **AC-6**: Header badge plus dashboard card show the live balance, and a low balance banner appears under 10 credits with a buy link.
* **AC-7**: Onboarding welcome grant still applies once per student as a PROMOTIONAL_CREDIT ledger entry and coexists with paid CREDIT_PURCHASE entries.
* **AC-8**: Admins can create, edit price and credits, and activate or deactivate packages; inactive packages never appear to students and never start checkouts.
* **AC-9**: Payment started, webhook received, credits allocated, payment failed or expired, and refund issued each write an AuditEvent row with payment id, package id, amount, and actor.
* **AC-10**: A failed AI run refunds its held credits automatically with a REFUND ledger entry keyed as refund plus debit reference, and a duplicate refund attempt is a no op.
* **AC-11**: Sandbox keys drive test traffic and live keys drive production with no code change beyond environment values.

## Decision

**Chosen option**: Option 1: Direct collect prompt with polling

Build the direct collect prompt flow against Fapshi sandbox first, then swap to live keys. Keep the single `CreditLedger` table with `balanceAfter` and the unique guard, reuse the existing `Payment` and `PaymentWebhookEvent` tables with small additive columns, and keep refunds limited to failed AI runs in this slice.

## Feature design

**Data model sketch**:

Reuse existing tables with additive columns only, no rebuild. Enums `LedgerType` (CREDIT_PURCHASE, OPERATION_DEBIT, PROMOTIONAL_CREDIT, REFUND, ADMIN_ADJUSTMENT) and `PaymentStatus` (PENDING, SUCCESSFUL, FAILED, EXPIRED) already exist.

* `CreditPackage` (reuse plus seed): `id`, `name` (req), `priceXaf` int (req), `credits` int (req), `isPopular` bool, `isActive` bool, `sortOrder` int, `createdAt`, `updatedAt`. Seed three rows per AC-1. Students read only active rows ordered by `sortOrder`.
* `Payment` (reuse plus add): existing `id`, `userId` FK cascade (req), `packageId` FK (req), `amountXaf` int copied from package at start (req), `creditsAllocated` int copied from package (req), `status` (req), `provider` default fapshi, `providerTransId` unique when set (opt, set at Fapshi accept), `payerPhone` normalized 237 form (opt), `paymentUrl` (opt, unused in direct collect, keep null), `failureReason` (opt), `createdAt`, `completedAt` (opt). New: `clientKey` text (req, UUID v4 generated by the client per checkout attempt; resending the same key returns the existing row with 409), `expiresAt` DateTime created plus 30 minutes (req, new), `webhookVerifiedAt` DateTime (opt, new).
* `PaymentWebhookEvent` (reuse plus add): existing `id`, `paymentId` FK (opt), `eventType` (req), `payload` Json (req), `isProcessed` bool, `createdAt`. New: `signatureValid` bool (req, new, false when rejected), `providerTransId` text (opt, new, indexed for lookup before payment row links).
* `CreditWallet` (reuse, no change): `id`, `userId` unique, `balance` int, `updatedAt`.
* `CreditLedger` (reuse, no change): `id`, `walletId` FK cascade, `type`, `amount` int (positive for purchase, promo, refund; negative for debit), `balanceAfter` int, `description`, `referenceId` (opt), `metadata` Json, `createdAt`. Uniqueness stays (`walletId`, `referenceId`, `type`).
* Indexes: existing (`Payment.userId`, `status`; `CreditLedger.walletId`, `createdAt`). New: (`Payment.expiresAt`) for the expiry job, (`Payment.clientKey`, `userId`) for safe retry lookup.
* Uniqueness for money safety: (`userId`, `clientKey`) on Payment so a retried start returns the existing row; ledger (`walletId`, `referenceId`, `type`) blocks double credit; partial unique index on `providerTransId` where not null blocks double accept.

**State transitions**:

`PENDING` to `SUCCESSFUL` (webhook verified, credits allocated, `completedAt` set) or to `FAILED` (Fapshi reports failure, `failureReason` set) or to `EXPIRED` (expiry job passes `expiresAt` while still `PENDING`). `SUCCESSFUL`, `FAILED`, and `EXPIRED` are terminal and never transition again. A late SUCCESSFUL webhook arriving after `EXPIRED` allocates nothing; it writes an event row plus an audit row flagged for manual reconcile. Retry means a POST with a fresh `clientKey` creating a new row; the old row stays terminal. Credit allocation happens only on the single transition into `SUCCESSFUL`, inside one DB transaction that locks the payment row first (SELECT FOR UPDATE), then flips the payment row and writes the ledger row plus audit row.

**Provider status mapping** (confirm field names against the live sandbox before build task 3): Fapshi success maps to `SUCCESSFUL`; Fapshi failure or cancel maps to `FAILED` with `failureReason` copied from the provider message; an unknown status maps to `FAILED` with a generic reason. The status poll endpoint and the expiry job both query Fapshi server side and apply this mapping, so polling never trusts client state alone.

**Key invariants**:
* Credits allocate only on a verified webhook transitioning a PENDING row to SUCCESSFUL, once per payment.
* The webhook transaction locks the payment row first, so concurrent retries serialize on the lock and unique constraints backstop any race.
* `balanceAfter` on every ledger row equals the wallet balance after that row commits.
* Ledger (`walletId`, `referenceId`, `type`) stays unique; Payment `providerTransId` stays unique where set.
* Terminal payments never change state; retry always creates a new row with a fresh `clientKey`.
* Expired or failed payments never allocate credits; a late success after expiry only writes audit for manual reconcile.
* Phone input strips spaces, dashes, and plus, accepts 9 digit 6XXXXXXXX and 2376XXXXXXXX, normalizes to 237XXXXXXXXX, and anything else gets 422.
* Amount and credits on a Payment are snapshots copied at start, so later package edits never alter open checkouts.
* Deactivating a package blocks new starts but open PENDING rows resolve normally.
* The welcome grant keeps the amount and timing decided in onboarding; this slice only requires coexistence with paid entries.

**Security model**:

Students read only their own wallet, ledger, and payments (owner scoping by session user id, others get 403 plus an audit row). Package list shows only active rows to students; full CRUD stays admin only through the existing `requireAdmin` guard. The webhook endpoint carries no session and trusts only the HMAC SHA256 signature over the raw body checked with a timing safe compare (header name confirmed against the live sandbox); missing or bad signatures get 401 and a `PaymentWebhookEvent` row with `signatureValid` false, and no state changes. Money endpoints carry Arcjet rate limits reusing the auth and wizard route patterns (start payment strict per user per minute, webhook per IP) with 429 on excess. Audit vocabulary is fixed: payment.started, payment.webhook.received, payment.credited, payment.failed, payment.expired, payment.refunded; actor is the user for starts and system for webhook and cron rows, with amount in XAF plus credits. Compliance scope is payments plus PII (phone numbers, payment amounts): phone stored in normalized form only, full webhook payloads stored for reconciliation but never returned to clients, and every money mutation writes an AuditEvent.

**Configuration required**:
* `FAPSHI_API_KEY`: Fapshi server key for direct collect calls
* `FAPSHI_WEBHOOK_SECRET`: HMAC secret used to verify webhook signatures
* `FAPSHI_BASE_URL`: sandbox URL for test traffic, live URL for production
* `FAPSHI_CURRENCY`: fixed to XAF
* `PAYMENT_EXPIRY_MINUTES`: fixed at 30, override only in tests
* `CRON_SECRET`: shared secret guarding the expiry job endpoint
* `LOW_BALANCE_THRESHOLD`: fixed at 10 credits for the banner rule

**Critical test scenarios** (each maps to an acceptance criterion in ## Requirements):
* Happy path: pick Standard package plus valid MoMo number plus approve prompt plus verified webhook credits 150 once and balance updates, verifies AC-1, AC-2, AC-3, AC-6
* Failure case: Fapshi retries the same webhook three times and only one ledger row exists, verifies AC-3
* Failure case: unpaid payment passes 30 minutes and the job marks it EXPIRED with no credits, verifies AC-4
* Failure case: failed payment shows reason and retry creates a new payment row, verifies AC-5
* Auth/permission: one student reads another student's payment or ledger and gets 403 plus an audit row; unsigned webhook gets 401 with no state change, verifies AC-9
* Refund path: failed assistant run after hold writes one REFUND row and a repeat refund call changes nothing, verifies AC-10

## Build plan

Ordered as a Tracer Bullet (thin end to end thread through every layer first, then thicken). Each task names the ACs it satisfies.

1. Seed the three packages plus package read route with active only ordering, satisfies AC-1, AC-8
2. Thin thread: start payment with phone normalize plus Fapshi direct collect call plus Payment row with clientKey and expiresAt, satisfies AC-1, AC-2
3. Webhook verify plus allocate: HMAC check plus event row plus single transaction flipping payment to SUCCESSFUL and writing CREDIT_PURCHASE ledger plus audit, satisfies AC-3, AC-9
4. Status poll with server side Fapshi status query plus balance read plus header badge wiring, satisfies AC-2, AC-6
5. Expiry job that queries Fapshi before marking EXPIRED plus failed and expired UX with retry as new payment, satisfies AC-4, AC-5
6. Ledger history page plus pagination plus low balance banner plus welcome grant coexistence check, satisfies AC-6, AC-7
7. Admin package CRUD plus inactive hiding plus audit coverage for all money events, satisfies AC-8, AC-9
8. Refund wiring for failed AI runs reusing existing hold helpers plus sandbox to live key swap runbook, satisfies AC-10, AC-11

## Consequences

**Positive**:
* Real money path unblocks all paid AI work with one audited ledger.
* Exactly once guards plus HMAC verification make retries safe by construction.
* Snapshot amounts on Payment keep open checkouts stable when admins reprice.

**Negative / tradeoffs**:
* Direct collect only means operator prompt failures need clear retry UX; hosted page fallback waits for a later slice.
* Webhook payload storage grows with traffic and needs the same retention and prune discipline as other event tables.
* Sandbox behavior may differ slightly from live operator behavior, so live verification with small amounts stays required.

**Neutral**:
* New env values for Fapshi plus a cron entry for expiry need provisioning before build starts.
* Admin package edits are immediate for new checkouts and never rewrite history.
